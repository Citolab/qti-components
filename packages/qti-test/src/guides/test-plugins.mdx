# Creating a plugin

A **test plugin** is a set of custom elements you add to a `<qti-test>` that use only the test's
public API. The test's own code does not know about it: nothing in the core imports or refers to it.
Delete the plugin and nothing in the test needs to change.

The plugins in this repository live in two packages. `@qti-components/test` keeps one (submit) and registers them with the rest of its elements. The others (the navigation links, stamp, the scoring, print and view helpers, bookmark, text-to-speech, zoom and the character sheet) are
`@qti-components/extended`, a package of its own that is not part of `@citolab/qti-components`: install it next to the umbrella and import it once
(`import '@qti-components/extended'`). It registers only its own tags, so it loads in any order next
to the package root or `/corrections`.

Write a plugin when you add something _to_ a test — reading aloud, a scoring aid, a debug panel.
When you need to change how the test itself behaves, a plugin is the wrong tool: that is a change
to the test, or a subclass registered under the same tag (as `@citolab/qti-components/corrections`
does).

This is the code the story above runs, and its play test is the check that the API it uses still
works. Three things to notice:

1. **It reads one context.** `computedContext` says which item is active (`active`) and where it
   is rendered (`itemElement(identifier)`). It never calls `closest('qti-test')` or looks inside
   `test-container` — `closest` stops at shadow roots, and where the test keeps its items is the
   test's business.
2. **It has nothing to listen for.** The context updates on navigation, and again once the new
   item has rendered, so `render()` simply runs again with the right item.
3. **It imports only public API**: `lit`, `@lit/context`, and `computedContext` from
   `@qti-components/base` (`@citolab/qti-components/qti-base` for umbrella users).

## The public test API

### One context: `computedContext`

A plugin reads `computedContext` with `@consume({ context: computedContext, subscribe: true })`.
`test-navigation` provides it, so **a plugin lives inside `<test-navigation>`** — anywhere inside
it, also inside the item-ref templates, because a context request crosses shadow roots.

| Member                                                        | Gives                                                                     |
| ------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `identifier`, `title`, `view`                                 | The test, and who is looking (`candidate`, `scorer`, …)                   |
| `testParts[].sections[].items[]`                              | The structure, with `active` on the part, section and item that are shown |
| an item: `index`, `valid`, `done`, `completionStatus`, score… | The state of each item                                                    |
| `itemElement(identifier)`                                     | The rendered `qti-assessment-item`, or `null` when it is not on the page  |

`itemElement` looks the item up when you call it, so ask again after each update: an item that is
rendered again is a new element. It is a function, so `JSON.stringify` of the context leaves it
out.

The other contexts are not for plugins. `sessionContext` holds the same position and `view` as
ids; `testContext` is the responses and outcomes model that hosts persist; `configContext` and
`qtiContext` are what a host sets up.

### Events to send

Dispatch with `bubbles: true, composed: true`. The element that handles it must be an ancestor.

| Event                    | `detail`                                            | Handled by        | Sent by (for reference)       |
| ------------------------ | --------------------------------------------------- | ----------------- | ----------------------------- |
| `qc-test-navigate`       | `{ type: 'item' \| 'section', id }`                 | `qti-test`        | `test-next`, `test-item-link` |
| `qc-test-end-attempt`    | —                                                   | `test-navigation` | `test-end-attempt`            |
| `qc-test-submit`         | —                                                   | `qti-test`        | `test-submit`                 |
| `qc-test-update-outcome` | `{ assessmentItemRefId, outcomeVariableId, value }` | `test-navigation` | `test-scoring-buttons`        |
| `qc-test-switch-view`    | the `View`                                          | `qti-test`        | `test-view`                   |

`dispatchPublic` and `listenPublic` (`@citolab/qti-components/qti-test/plugin-api`) send and handle the 9.x
names (`cito-test-navigate`, `cito-test-end-attempt`, …) alongside these until the next major. The 7.x
names (`qti-request-navigation`, `test-end-attempt`, …) are gone.

### Keeping state

A plugin that must remember something across a reload (bookmarks, notes) keeps it in the test's
state, under its own name, and does not store anything itself:

- **Write:** dispatch `qc-test-update-plugin-state` with `{ plugin: 'bookmarks', value: [...] }`.
  The value is stored as JSON (a copy, so changing it afterwards changes nothing); `null` removes the
  entry. A value that is not JSON is ignored with a warning.
- **Read:** `computedContext.plugins` (or `pluginState(computedContext, 'bookmarks')`, typed). It is
  `{}` until a plugin has written.
- **Persist:** nothing to do for the plugin. The entry is part of `qtiTest.state.session.plugins`, so a
  host that already stores `state` (and listens to `qc-test-state-changed`) stores it, and assigning
  that state back restores it. Entries of plugins that are not loaded are kept, so a round trip never
  drops another plugin's data.
- **Type it:** inside `@qti-components/test`, augment `QtiTestPluginState` with your entry
  (`interface QtiTestPluginState { notes: string[] }` in a `declare module` on `types/qti-test-state`) and
  read it with `pluginState`. In a package of its own, read `computedContext.plugins.<name>` and check its
  shape in one typed helper (see below); the test itself never reads an entry.

`<test-bookmark>` (`packages/qti-extended/src/test-bookmark/`) is the worked example: `bookmarkedItems`
reads `plugins.bookmarks` and keeps only strings, and the button writes the new list with
`qc-test-update-plugin-state`.

Keep an entry small and plain: it is stored with the candidate's data, so it is not for the answer key or
for anything the host should rederive.

### From another package: `@citolab/qti-components/qti-test/plugin-api`

A plugin in its own package takes what it needs from one entry, which registers nothing:
`dispatchPublic`, `listenPublic` and `PUBLIC_EVENTS` with their types, `pluginState`, the
`QtiTestState` and `QtiTestPluginState` types, and `controlStyles`, the look of the test controls
(`controlStyles.button` with `controlStyles.control` draws a button like `<test-next>`).
`computedContext` comes from `@citolab/qti-components/qti-base`, and the public elements are types from
`@citolab/qti-components/qti-test`.

Import them through the umbrella, `@citolab/qti-components`, and make it a **peer dependency**, not
`@qti-components/base` or `@qti-components/test` as dependencies. The umbrella bundles its own copy of
those packages, and the contexts are keyed with a `Symbol()` of each copy: a plugin that installs a
second copy asks for a key the test never provides, and silently never gets the context.
`@qti-components/extended` is built this way. For the same reason, type your state entry where you
read it (as `zoomLevel` and `bookmarkedItems` do) rather than by augmenting `QtiTestPluginState`: the
umbrella's bundled types keep the interface `pluginState` reads in an internal chunk.

### Not public

Do not use these from a plugin; they change without notice:

- anything under `@qti-components/test/internal` (such as `testHostContext`);
- `sessionContext`, `testContext`, `configContext` and `qtiContext` (see above);
- `test-container`'s shadow root, or any other component's;
- the styles module itself (`components/styles`); take `controlStyles` from the plugin API.

## Naming

Tags starting with `qti-` belong to the 1EdTech QTI vocabulary — never use them. Plugins in this
repository use `test-`. Your own use your own prefix.

## Packaging a plugin in this repository

A plugin is a set of files, and only those files and one line in its package's elements entry know it
exists. A new plugin goes in `@qti-components/extended`, in `src/<element>/`; `@qti-components/test` keeps
only submit, in `components/<element>/`, listed
in `plugins/elements.ts`. Something for the candidate beyond the QTI specification goes in
`@qti-components/extended`, in `src/<element>/`, listed in its `elements.ts` (`qtiExtendedElements`);
text-to-speech (`packages/qti-extended/src/tts/`) is the reference there. A class there is also listed
in the JSX-types `exclude` in `cem.config.mjs`, because the umbrella's React types do not cover that
package.

The rest of this section is about `@qti-components/test`.

`plugins/elements.ts` is the one place that composes them: it re-exports each plugin's classes and
lists their `{ tag, ctor }` entries as `pluginElements`. `qti-test`'s own `elements.ts` spreads
`pluginElements`, and `register.ts` defines them with everything else. A scoped
`CustomElementRegistry` (a plugin placed inside an item-ref template is stamped into
`test-container`'s shadow root, which uses the registry you give it) takes the entries from
`@qti-components/test/plugins/elements` or from `@qti-components/test/elements`.

Wiring a new plugin:

- `packages/qti-test/src/plugins/elements.ts`: its import, export and entry in `pluginElements`;
- tooling, when it has its own folder: a `directory` entry in `.storybook/main.ts`, and a glob plus a
  `componentTypePath` row in `cem.config.mjs`;
- the boundary spec: one entry in `PLUGINS` in `packages/qti-test/src/plugin-boundary.spec.ts` (its
  package, folders and a pattern that matches anything naming the plugin).

That entry is what keeps a plugin a plugin: without it, the first convenient import from the test
into the plugin, or from the plugin into the test's internals, goes unnoticed.

A plugin outside this repository needs none of this: depend on `@qti-components/base`, define
your elements, and place them inside `<test-navigation>`.
