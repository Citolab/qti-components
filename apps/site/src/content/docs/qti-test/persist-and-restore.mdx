---
title: Persist & restore
description: Save a candidate's test session and resume it later — qtiTest.state and the qc-test-state-changed event.
---

A `<qti-test>` has one property and one event for this. Where you store the state is up to you.

```js
const qtiTest = document.querySelector('qti-test');

// Restore. Safe to assign before the test has loaded.
const saved = await load(candidateId);
if (saved) qtiTest.state = saved;

// Save. Fires on every change, so debounce writes to a backend.
qtiTest.addEventListener('qc-test-state-changed', e => save(candidateId, e.detail));
```

**Pass the same `seed` in `qtiContext` when resuming**, or the test selects other items
(`qti-selection`) and items and choices come back in a different order. Answers in a state for items
the test does not present are not restored, with a console warning. Config, `qtiContext` and `view` are not part of the state; you supply them on every load.

Assign the state before the test loads where you can: a PCI that is already on screen only picks up
a new state when its item loads again.

## The state

```ts
interface QtiTestState {
  version: 1;
  test: {
    items: {
      identifier: string; // the qti-assessment-item-ref identifier; a with-replacement clone's is item-3#2
      variables: {
        identifier: string;
        type?: 'response' | 'outcome' | 'template' | 'context';
        value: string | string[] | null;
      }[];
      state?: Record<string, string | null>; // per-interaction state, e.g. a PCI's getState()
    }[];
    outcomes: { identifier: string; value: string | string[] | null }[];
  };
  session: { navPartId?: string | null; navSectionId?: string | null; navItemRefId?: string | null };
}
```

Values only: no answer key, no declaration metadata. Treat it as opaque and store it as-is. An item
that `qti-selection with-replacement="true"` presents more than once has an entry per instance: the
first under its item-ref identifier, a clone under its instance id (`item-3#2`), which is also what
`navItemRefId`, `navigateTo('item', …)` and `updateItemVariables` take.

A value that is not a version 1 state is ignored, and the test sends `qc-test-state-refused` with
`{ message, state }`, once it has loaded. Log it, or tell the candidate their answers could not be
restored:

```js
qtiTest.addEventListener('qc-test-state-refused', e => report(candidateId, e.detail.message));
```

## Resuming a state stored as contexts

A host that stored `testContext` (and `sessionContext`, or only the item it was on) in 9.x turns it
into a state with `stateFromContexts`, and assigns that:

```js
import { stateFromContexts } from '@citolab/qti-components';

const stored = await load(candidateId); // { items: [...], navItemId: 'item-3' }, as saved in 9.x
qtiTest.state = stateFromContexts(stored, { navItemRefId: stored.navItemId });
```

It keeps the values only and writes them as strings, so a number stored as a JSON number reads back
as text. Save the new `state` from then on.

## Setting a single value

To change values on one item from outside the session, such as a score from manual scoring, use
`updateItemVariables`. It also fires `qc-test-state-changed`.

```js
qtiTest.updateItemVariables('item-ref-1', [{ identifier: 'SCORE', value: '1' }]);
```

## Replaces

`qti-test-context-updated` and reading or writing `testContext` for persistence are deprecated.
They expose the full test context, including the answer key.
