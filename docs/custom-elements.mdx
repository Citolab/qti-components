# custom element manifest

The project generates a [custom elements manifest](https://github.com/webcomponents/custom-elements-manifest)
(`custom-elements.json`) that describes every element: its attributes, properties, events, slots,
CSS parts and custom properties. It is built from the source and its JSDoc by the
custom-elements-manifest analyzer with the `@wc-toolkit` plugins configured in `cem.config.mjs`.

## Generating it

```sh
pnpm run cem
```

This writes `custom-elements.json` to the repository root and the JSX types to
`packages/qti-components/dist/qti-components-jsx.d.ts`.

The manifest is a **build output and is not committed** (it is in `.gitignore`). Everything that
needs it generates it first:

- `pnpm storybook` and `pnpm build-storybook` (Storybook reads it for the controls and API tables;
  `pnpm storybook` also keeps it up to date with the analyzer in watch mode);
- the Vitest `stories` and `vrt` projects (a global setup generates it when it is missing);
- `pnpm lint:vocab`, which reads the tag names from it;
- `pnpm build`, through the umbrella package's JSX types step.

If Storybook's API tables look out of date, run `pnpm run cem`.

## Editor support

With the [Web Components Language Server](https://marketplace.visualstudio.com/items?itemName=wc-toolkit.web-components-language-server)
extension, the root `wc.config.js` points at the generated `./custom-elements.json`, so run
`pnpm run cem` once after cloning.

## For consumers of `@citolab/qti-components`

The manifest itself is **not published**: its module paths point at this monorepo's sources
(`packages/qti-base/src/...`), which do not exist in the package. What the package does ship is the
JSX declarations generated from it, exported as `@citolab/qti-components/react`
(`dist/qti-components-jsx.d.ts`).
